# Ingestion Agent Report

This document outlines the design, role, constraints, and complete workflow of the **Ingestion Agent** within the Multi-Agent-BI-Engine.

## 1. What Exactly The Ingestion Agent Is
The Ingestion Agent (`backend.agents.ingestion_node`) is the foundational first step of the Multi-Agent Swarm pipeline. It acts as the bridge between raw user-uploaded data and the semantic, structured metadata required by downstream agents (like Cleaning, Featuring, and Analytics). It combines the brute-force processing power of DuckDB with the semantic inference capabilities of an LLM.

## 2. What it Does in the Whole Project
The primary responsibilities of the Ingestion Agent are:
- **Data Loading:** Safely loading the raw dataset from a remote storage location into an in-memory SQL database (DuckDB).
- **Statistical Profiling:** Calculating column-level statistics (null percentages, unique value percentages) and extracting non-null sample rows.
- **Semantic Inference:** Determining what each column *means* in a business context (e.g., identifying a float column as a "Currency" or "Percentage", or labeling it as a candidate KPI) based on the user's `business_domain`.
- **Caching:** Generating schema fingerprints and using vector embeddings to recall previously inferred schemas, avoiding redundant and costly LLM calls for familiar data structures.

## 3. Data Formatting and Input (How Users Provide Data)
The Ingestion Agent does not accept direct raw binary uploads in its Python state. Instead, it expects a pointer to the data.

**Accepted File Formats (`file_type`):**
- `csv`
- `parquet`
- `xlsx` (Excel)
- `json`, `jsonl`, `ndjson`

**Delivery Mechanism:**
The user/frontend must upload the file to a Supabase Storage bucket and pass a **Signed URL** (`raw_file_path`) in the `AgentSwarmState`. The agent streams the data directly from this URL into memory using DuckDB's HTTPFS extensions, or downloads bytes via HTTPX as a fallback.

## 4. How Data Should NOT be Used (Rejected Formats & Constraints)
- **Unsupported Extensions:** Passing a `file_type` outside of the accepted list (e.g., XML, TSV, HTML) will immediately raise an `Unsupported file type` error and halt the pipeline.
- **Missing Domain Context:** While the system won't explicitly crash, providing an "unknown" `business_domain` drastically reduces the accuracy of the LLM's semantic inference, particularly for identifying KPIs.
- **Massive Schema Context:** Passing thousands of columns into the LLM is restricted. The agent compresses schema descriptions down to ~600 tokens using a markdown table compressor (`compress_column_meta_for_prompt`) to prevent LLM context-window overflow and hallucination.

## 5. Rules and Constraints of the Ingestion Agent
The Ingestion Agent enforces strict boundaries on how it interprets and categorizes data, primarily driven by its LLM System Prompt (`prompts/ingestion.txt`):

1. **Semantic Type Constraints:** Every column MUST be classified into one of the following strict types:
   `identifier`, `metric`, `dimension`, `date`, `currency`, `percentage`, `boolean`, `text_description`, `geographic`, or `unknown`.
2. **Business Labeling:** Column names must be transformed into human-readable PascalCase format (e.g., "monthly_rev" becomes "Monthly Revenue").
3. **KPI Identification:** `is_candidate_kpi` must be evaluated purely based on domain conventions (e.g., "churn_rate" in SaaS), completely independently of whatever the user's specific analytical query might be.
4. **Sample Values:** The profiler extracts up to 5 non-null samples, but compresses this to a maximum of 2-3 sample values when prompting the LLM to save tokens.
5. **Output Structure:** The LLM MUST return strictly valid JSON matching the `ColumnMeta` Pydantic schema. No markdown wrappers or preamble are allowed.

## 6. The Complete Ingestion Workflow (From User to Cleaning Agent)

Here is exactly how the data flows from the user to the next stage in the pipeline:

### Step 1: State Initialization & Context Slicing
The agent receives the `AgentSwarmState`, slicing the context to extract `raw_file_path`, `file_type`, and `business_domain`.

### Step 2: In-Memory Database Load
The `DuckDBEngine` executes a query (e.g., `SELECT * FROM read_csv_auto(...)`) to load the remote data from the Supabase URL into an active, in-memory table. It records the `raw_row_count` and `raw_col_count`.

### Step 3: Statistical Schema Profiling
The `SchemaProfiler` kicks in. For every column, it runs `APPROX_COUNT_DISTINCT` and `COUNT` to calculate `null_pct` and `unique_pct`. It pulls up to 5 non-null sample rows. At this stage, the exact SQL data types are known, but the semantic types are left as "unknown".

### Step 4: Fingerprinting and Cache Check
A `schema_fingerprint` is generated by hashing a sorted list of the column names and their data types.
The agent uses the `EmbeddingEngine` to vectorize the basic schema and searches for similar previously processed schemas.
- **Cache Hit (Similarity > 0.92):** The LLM step is skipped. Metadata is instantly loaded from the vector database.
- **Cache Miss:** The agent proceeds to Step 5.

### Step 5: LLM Semantic Inference
The statistical metadata is passed through `schema_compressor.py` to create a dense, token-efficient Markdown table. The `LLMRouter` invokes the LLM (`SCHEMA_INFERENCE` task), asking it to assign a `semantic_type`, `business_label`, and `is_candidate_kpi` to every column based on the `business_domain`.

### Step 6: Output & Handoff to Cleaning Agent
The LLM's semantic JSON output is merged back with the concrete statistical data to form the final array of `ColumnMeta` objects.
The `AgentSwarmState` is updated:
- `column_metadata`: The full array of `ColumnMeta`.
- `pipeline_status`: Changed to `"ingesting"`.
- `current_agent`: Set to `"ingestion"`.

**State Handoff:** The state dictionary is returned. The actual underlying dataset remains loaded in the DuckDB in-memory engine, ready for the **Cleaning Agent**, which will use the `column_metadata` (e.g., `null_pct`, `dtype`) to write specific Polars/SQL data cleaning operations.
