4. DuckDB SQL syntax & Analytical Best Practices:
   - Use double quotes for column names with spaces or reserved words (e.g. "Order Date").
   - For breakdown and composition queries, NEVER exclude NULL or missing categories in the WHERE clause, as this causes the chart sum to disagree with the headline KPI total. Instead, coalesce them: `COALESCE(dim, 'Unassigned / Missing')` in both SELECT and GROUP BY. Only filter out NULLs in WHERE clauses for date/time columns in time-series queries.
   - For headline KPI queries (priority 1), compute COUNT(*) AS total_records over all records. If an identifier column exists (such as patient_id, employee_id, customer_id, order_id), compute BOTH COUNT(*) AS total_records (for total records/admissions/events) AND COUNT(DISTINCT id_col) AS unique_<entities> (for distinct unique entities). NEVER conflate total records with distinct entity count or label COUNT(*) as Total <Entities> when duplicates exist. Aggregate candidate KPI numeric metrics (e.g. ROUND(SUM(COALESCE(metric_col, 0)), 2) AS total_<metric>, ROUND(AVG(metric_col), 2) AS avg_<metric>) using ONLY columns that exist in the provided schema. Never assume hardcoded metric names like sales_amount, revenue, or salary. Never apply restrictive WHERE filters to headline KPIs that artificially reduce the total record count.
   - For time series, filter WHERE date_col IS NOT NULL, use STRFTIME(DATE_TRUNC('month', date_col), '%Y-%m') AS period, and ALWAYS ORDER BY period ASC. NEVER group by bare month numbers (1-12) across multi-year datasets, which incorrectly combines different years into single buckets and distorts trends.
   - Handle division by zero using NULLIF(col, 0) and COALESCE(...).
   - MATHEMATICAL INTEGRITY FOR RATIOS, PERCENTAGES, AND MARGINS:
     When aggregating ratios, percentages, margins, or rates (such as profit margin, margin_pct, discount rate, conversion rate) across groups, time periods, or for headline KPI cards:
     NEVER compute an unweighted arithmetic average of row-level percentages (e.g. `AVG(profit_margin_pct)` or `AVG(margin)`), because averaging row-level percentages produces severe distortion when row sizes differ.
     ALWAYS compute the true weighted aggregate ratio: `ROUND(SUM(numerator) / NULLIF(SUM(denominator), 0) * 100, 2)` (for example: `ROUND(SUM(profit) / NULLIF(SUM(total_order_value), 0) * 100, 2)` or `ROUND(SUM(profit) / NULLIF(SUM(sales_amount), 0) * 100, 2)`).
     In comparative benchmark queries (priority 5) comparing group margins against the overall dataset benchmark:
     Use `ROUND(SUM(profit) / NULLIF(SUM(COALESCE(total_order_value, sales_amount)), 0) * 100, 2) AS category_profit_margin_pct` and `ROUND((SELECT SUM(profit) / NULLIF(SUM(COALESCE(total_order_value, sales_amount)), 0) * 100 FROM data), 2) AS overall_profit_margin_pct`.
   - For binary 1/0 indicator rates, compute rates as ROUND(AVG(col) * 100.0, 1).
   - NEVER multiply an existing percentage/discount column by 100! If a column already represents percentages (such as discount, discount_pct, bonus_pct, tax_rate with values like 5, 10, 20), compute averages directly: ROUND(AVG(discount), 2). Multiplying by 100 produces completely invalid numbers like 280%!
   - NEVER use pie charts for rates or percentages across categories because separate rates do not sum to 100%. Use sorted bar charts instead.
   - NEVER use geographic coordinates (latitude, longitude, lat, lon, coord), phone numbers, fax numbers, zip codes, postal codes, or identifiers as measurable business metrics! You must NEVER compute SUM(latitude), AVG(latitude), or use coordinates on chart y-axes or headline KPIs. Coordinates are spatial location attributes, NOT financial, volume, or performance measures. Focus on genuine business metrics (revenue, sales, profit, quantity, headcount, salary, cost, ratings, tenure, discount, etc.).
   - For anomaly queries, identify records deviating significantly from the mean on a primary numeric metric using realistic statistical outlier bounds (e.g. WHERE col >= (SELECT AVG(col) + 1.5 * STDDEV_POP(col) FROM data) ORDER BY col DESC LIMIT 10) so genuine statistical outliers are displayed without returning 0 rows. Ranked outlier transactions with entity identifiers must always have chart_type = 'bar' (or 'data_table'), NEVER 'heatmap'. The chart title MUST NOT claim a fixed count like "Top 10" because statistical thresholds may return fewer or more rows; instead use titles like "Statistical Outliers by [Metric]" or "High [Metric] Outliers". Select primary identifiers (e.g. order_id, patient_id, employee_id) rather than raw personal names (PII).
   - For comparative benchmark queries (priority 5), define the comparison formula explicitly: Prefer raw metric comparisons (e.g. SELECT dim, ROUND(AVG(metric), 2) AS category_avg, ROUND((SELECT AVG(metric) FROM data), 2) AS overall_avg FROM data WHERE dim IS NOT NULL AND dim NOT IN ('Unknown', 'Unspecified', 'N/A') GROUP BY dim ORDER BY category_avg DESC LIMIT 6). If computing percentage deviation from overall average, use ROUND(((AVG(metric) - (SELECT AVG(metric) FROM data)) / NULLIF((SELECT AVG(metric) FROM data), 0)) * 100, 2) AS pct_deviation_from_overall with baseline at 0%. If computing an index, use ROUND((AVG(metric) / NULLIF((SELECT AVG(metric) FROM data), 0)) * 100, 2) AS category_index with baseline at 100.

ANALYTICAL PURPOSE GUIDE:
- kpi: Single-metric headline summary or high-level status indicator (e.g., total headcount, total spend)
- trend: Progression, evolution, or patterns over time (e.g., monthly hiring rate, salary changes over years)
- comparison: Explicit benchmarking or comparative evaluation against averages/targets (e.g., department vs company avg)
- composition: Part-to-whole proportions or shares (e.g., headcount share by region, budget allocation)
- relationship: Correlation or association between two numeric measures (e.g., salary vs performance score)
- distribution: Spread, frequency, or variance across entities or bands (e.g., salary distribution, tenure spread)
- ranking: Ordered top/bottom performers or hierarchy (e.g., top 5 highest paid departments)
- breakdown: Categorical segmentation along dimensions (e.g., metrics sliced by department or region)
- anomaly: Outlier detection, irregularities, or unusual data points (e.g., employees with high tenure but low pay)
- detail: Granular tabular records or multi-attribute drilldowns

CHART TYPE SELECTION GUIDE:
- kpi_card: Single-row aggregate KPIs (e.g., total count, average salary)
- bar: Categorical comparisons (e.g., salary by department)
- line: Time-based trends (e.g., monthly hiring over time)
- area: Time-based cumulative trends
- pie: Part-to-whole proportions (e.g., employee distribution by region)
- scatter: Correlation between two numeric variables
- heatmap: Two-dimensional categorical cross-tabulation
- data_table: Detailed row-level data or complex multi-column breakdowns
- funnel: Sequential process stages

AXIS MAPPING RULES:
- For GROUP BY queries: x_axis = the grouped dimension column, y_axis = the aggregated measure
- For time-series: x_axis = the time column/alias, y_axis = the measured value
- For KPI/scalar: x_axis = null, y_axis = null, chart_type = "kpi_card"
- For scatter: x_axis = first numeric column, y_axis = second numeric column

PRIORITY RULES:
- Priority 1: The single most important KPI query (analytical_purpose: "kpi")
- Priority 2: Supporting trend queries (analytical_purpose: "trend")
- Priority 3: Segmentation/breakdown queries (analytical_purpose: "breakdown" or "composition")
- Priority 4: Anomaly detection (analytical_purpose: "anomaly")
- Priority 5: Benchmark comparisons (analytical_purpose: "comparison")
